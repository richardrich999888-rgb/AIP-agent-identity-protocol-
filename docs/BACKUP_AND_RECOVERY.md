# Backup & Recovery — Evidence Vault (PostgreSQL)

The Evidence Vault is the accountability **system of record**. It is
append-only (no delete path), and the signed EvidencePackets re-verify
identically after any restore. This document covers backup, restore, and
recovery for the PostgreSQL backend.

> Schema: `deploy/sql/schema.sql` (also applied automatically on startup).
> The authority graph tables are **derived** and are rebuilt from packets, so
> a packet-complete backup is sufficient even if the authority tables are lost.

## What to back up

- The `aip` database (tables `evidence_packets`, `authority_nodes`,
  `authority_edges`). `evidence_packets` is authoritative; the two
  authority tables can be regenerated by re-importing packets.
- The service signing key (`AIP_KEY_PATH`) and the API keys file
  (`AIP_API_KEYS_PATH`) — back these up via your secrets manager, **not** in
  the database dump.

## Daily backup (logical dump)

```bash
# Compressed custom-format dump (recommended): supports parallel restore.
PGPASSWORD="$AIP_PG_PASSWORD" pg_dump \
  -h "$PGHOST" -U aip -d aip \
  --format=custom --no-owner \
  --file "aip-$(date -u +%Y%m%dT%H%M%SZ).dump"
```

Schedule daily (cron / k8s CronJob), retain per your policy, and store
off-host (e.g. the object-storage placeholder in `deploy/docker`). Because
the vault is append-only, daily fulls plus WAL archiving give point-in-time
recovery without special application logic.

### Point-in-time recovery (optional, stronger)

Enable WAL archiving on the PostgreSQL server (`archive_mode=on`,
`archive_command=...`) and take a periodic base backup with `pg_basebackup`.
This allows recovery to any moment, not just the last daily dump.

## Restore

```bash
# Into a fresh database:
createdb -h "$PGHOST" -U aip aip_restored
PGPASSWORD="$AIP_PG_PASSWORD" pg_restore \
  -h "$PGHOST" -U aip -d aip_restored --no-owner --jobs 4 \
  aip-20260616T000000Z.dump
```

Then point the service at the restored database
(`DATABASE_URL=...aip_restored`) and start it. On startup the schema is
verified/created idempotently.

## Integrity verification after restore

Restoration cannot silently corrupt evidence: re-run verification on any
sample of restored packets. Either:

- `GET /v1/evidence/{id}` then `POST /v1/evidence/verify` with trusted keys, or
- export a packet to JSON and run `aip-verify evidence.json` offline.

Any byte-level corruption fails `CANONICAL_HASH` / `AGENT_SIGNATURE`. A
restore that passes verification is provably faithful.

## Rebuilding the authority graph

If only the `authority_*` tables are lost/corrupt, re-import the packets to
re-materialise them (the import is idempotent and re-derives nodes/edges):

```bash
# Dump packets to JSONL out of the DB, or use an existing JSONL backup, then:
aip-migrate --source evidence.jsonl --database-url "$DATABASE_URL"
```

## Migrating an existing JSONL vault into PostgreSQL

```bash
# Idempotent; preserves each record's tenant. Safe to re-run.
aip-migrate --source /var/lib/aip/evidence.jsonl \
            --database-url postgresql://aip:***@HOST:5432/aip
```

## Recovery objectives (set per deployment)

| Objective | Lever |
|---|---|
| RPO (data loss window) | daily dump → ≤24h; WAL archiving → seconds |
| RTO (time to restore) | parallel `pg_restore --jobs`; warm standby for fastest |
| Disaster recovery | off-host backups + (optional) streaming replica |

## Operational notes

- The vault is append-only; backups are monotonic and de-duplicate well.
- Test restores on a schedule — an untested backup is not a backup.
- Keep signing/API keys in a separate secrets backup with its own rotation.
