The inspected Microsoft repository is `4eca1f5b44d30ebe5e9745ac36ca394f887e617b`. These preview/alpha components are not described here as a finalized universal governance standard.

The live test builds the real Rust binding, loads an ACS manifest and Rego policy, then invokes `AgentControl.run_tool` around the provider's actual ContextForge call. An out-of-scope record is denied before dispatch. Valid input receives native pre/post decisions. The existing engine computes `input_identity` and `enforced_identity`; the bridge preserves them, the full verdict and any transformed target. It neither re-evaluates Rego nor converts transforms/warnings/approvals to a boolean.

`microsoft_result` consumes the actual `InterventionPointResult` dataclass or its serialized form. Tuple normalization changes JSON representation only. The older `correlate_decision_request` helper compares supplied strings only and is not a verification interface.

The new `compare_microsoft_receipt` bridge checks a narrower, executable profile. It calls the pinned upstream SDK's `action_identity` over the complete native policy input and requires both `input_identity` and `enforced_identity` to match. It accepts only untransformed pre-tool `tool_args` allow/deny records with matching snapshot arguments, explicit request/agent references and an operator-configured tool alias. It then calls the existing Rust receipt binary's public-key-only `compare-request` mode. Rust verifies the receipt signature and recomputes the argument commitment with the original gateway encoder, comparing agent, decision, tool and request IDs individually. No signing format or external protocol semantics change.

The fresh live workload maps the model's record ID to `{loan_id, amount}` **before** ACS evaluation and sends those exact evaluated arguments to ContextForge. The native `tool_call_id` is also the gateway request ID. Policy v2 permits only synthetic loan IDs 17/18, amount zero and those exact keys. Four Rego tests cover this scope. Two fresh lab runs completed; the retained final run has four genuine model generations, 28 gateway checks/receipts and five live authentication/governance negatives. Its reported ACS input matches its actual signed gateway request offline. The new 25-case archive suite also exercises changed arguments, replayed receipt context, cross-tenant requests, wrong anchors, forged receipts, missing identities, policy changes, misleading authenticity declarations and unsupported verdict/numeric profiles.

This is **content consistency**, not an authenticated policy decision. Anyone able to fabricate an ACS application record can also recompute its unkeyed input digest; a test explicitly preserves that limitation. The returned governance-source and policy-version authenticity remain `NOT_ESTABLISHED`, even when an imported record claims otherwise. The lab alias and logical-agent mapping are not independently authenticated. Receipt v1 has no tenant field: tenant-scoped gateway anchors must be provisioned by the assessor, never taken from the untrusted event. A matching `Refused` or `Failed` receipt retains that disposition. A reported denial with a forwarding disposition is a scoped divergence between those reports, not an independently proven unauthorized execution.

Transforms, approvals, other verdicts, post-tool decisions, floating-point arguments and integers outside ±(2^53−1) remain insufficient for this comparison profile. Native ACS events retain these original semantics; the bridge does not reinterpret them or evaluate policy. Missing request references in the earlier archive are not retroactively inferred.
