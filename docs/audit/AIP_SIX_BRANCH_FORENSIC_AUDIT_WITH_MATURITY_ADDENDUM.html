Principal finding · execution-proven

Containment cannot fire. The containment gate requires evidence strength Proven for a workload violation; the reconciliation engine caps every workload violation at Attested exactly. An exhaustive 32-cell sweep under a maximally permissive policy returns Contain in four cells — all four requiring a Reconciliation the engine cannot emit. What changed since the first revision

Both P0 findings — the missing verifier clock and the unbound delegation issuer — were closed by the production branch while the extension was being built, and were re-verified here rather than accepted on their commit messages. That verification found a new P1: the clock fix landed in aip-protocol and never reached aip-service, whose /verify endpoint still applies no temporal bound (B-1a, Extension 10). Report 11 records two deliverables that were incomplete when first reported — one of them wrongly reported as done — and closes both.

2. aip-core/src/capability.rs

2.1 canonical_token_payload — main

main/…/capability.rs:208-231. Reconstructed from the read:

buf.extend_from_slice(jti);              // 16 bytes, fixed — fine
buf.extend_from_slice(issuer_id.as_bytes());   // UNBOUNDED, NO PREFIX
buf.extend_from_slice(agent_id.as_bytes());    // UNBOUNDED, NO PREFIX
for action in &scope.allowed { … }
buf.push(0xFF);                          // separator a payload can contain
for action in &scope.denied { … }
buf.extend_from_slice(&issued_at.to_le_bytes());
// expires_at: ABSENT

encode_scope_action (main/…/capability.rs:232-242) encodes Custom(s) as 0x01 ‖ s ‖ 0x00.

Findings.

  • L-1 (P0). Adjacent unprefixed strings are not injective. ("ab","c") and ("a","bc") yield identical bytes.
  • L-2 (P0). expires_at is not in the signed preimage but is enforced by check_temporal_validity downstream. The verifier enforces a field the issuer never signed.
  • L-3 (P1). No domain tag. A ScopedToken signature and a DelegationToken signature over structurally similar content are interchangeable.
  • L-4 (P2). 0xFF is used as an allowed/denied separator and 0x00 as a custom-action terminator. Both are bytes a Custom(String) action can contain, so a custom action with an interior NUL is ambiguous with two adjacent actions, and the allowed/denied boundary is forgeable by a crafted action name.

All four are present on main, audit, importot, valladder, aipv4.

2.2 canonical_token_payload — prod

prod/…/capability.rs:221-238. All four findings closed:

put_domain(&mut buf, SCOPED_TOKEN_DOMAIN);   // L-3
buf.extend_from_slice(jti);                  // fixed 16
put_str(&mut buf, issuer_id);                // L-1
put_str(&mut buf, agent_id);                 // L-1
encode_scope(&mut buf, scope);               // L-4
put_u64(&mut buf, issued_at);
put_opt_u64(&mut buf, &expires_at);          // L-2

expires_at is computed once at :144 and threaded to both the payload and the struct, so the signed value and the carried value cannot diverge — a small detail that matters, because the previous code computed expires_in_ms.map(|d| now_ms + d) inline at the struct literal.

verify_scoped_token (:170-176) passes token.expires_at into the recomputed payload, so the check is closed on both sides.

Tests that genuinely exercise the property (:253-330, :424-490): test_mutate_expires_at_extend_rejected, test_mutate_expires_at_some_to_none_rejected, test_mutate_expires_at_none_to_some_rejected, test_token_payload_adjacent_ids_do_not_collide, test_token_payload_custom_action_interior_nul_unambiguous, test_token_payload_expiry_presence_is_distinct, test_token_payload_starts_with_domain_tag.

The interior-NUL test is the strongest of these: it distinguishes Custom("x\0y") from [Custom("x"), Custom("y")] from allowed=[Custom("x")], denied=[Custom("y")] — three arrangements that the old encoder could confuse.

3. aip-core/src/delegation.rs

3.1 verify_delegation_chain — prod, read in full

prod/…/delegation.rs:179-244. Five checks per hop, in this order:

#CheckLineError
1hop.parent_jti == prev_jti:200LineageInvalid
2hop.depth == i+1:206LineageInvalid
3is_scope_subset(hop.scope, prev_scope):211AttenuationViolation
4issuer signature over recomputed payload:219SignatureInvalid
5hop.expires_at does not outlive parent's:227-235AttenuationViolation

Finding L-5 (P0, all six branches). There is no check that hop.issuer_id equals the previous hop's grantee_id, or — for hop 0 — the root token's agent_id. The chain is linked by JTI and by depth. The identities are not linked. Any principal whose key is present in issuer_public_keys can present itself as the issuer of a hop whose parent_jti matches, and all five checks pass.

The consequence is precise: delegation is authenticated (someone with a trusted key signed this hop) but not attributed (that someone need not be the party the previous hop delegated to). A "chain of custody" that does not check custody.

Checked, not a finding — the depth bound is correct. The limit is if chain.len() >= MAX_DELEGATION_DEPTH (:190), and create_sub_delegation rejects new_depth >= MAX_DELEGATION_DEPTH (:120). With MAX_DELEGATION_DEPTH = 8 and root delegations starting at depth 1 (:77), the maximum accepted depth is 7. This initially reads as an off-by-one, and it is not: the module's invariant list states the bound as depth < MAX_DELEGATION_DEPTH (:18), a strict inequality, and both call sites implement exactly that. Recorded here because an automated scan and a first reading both flag it, and the next auditor should not have to re-derive the answer.

3.2 Ordering of check 4 before check 5 — correct, and deliberately so

The comment at :224-226 explains it:

checked after authenticity so a forged expiry is reported as SignatureInvalid, and an issuer that genuinely over-delegated is reported as AttenuationViolation.

This is right. The two conditions are different accusations — tampering versus exceeding authority — and collapsing them would destroy forensic information. test_legitimately_signed_hop_outliving_parent_rejected (:520-575) pins it by forging a hop with the genuine delegating key and requiring AttenuationViolation specifically, with a control case at equal expiry that must succeed.

4.2 R15 — read in full

fn check_execution_binding(packet, e) -> bool {
    let Some(b) = &packet.execution_binding else {
        return e.record(EXECUTION_BINDING, true,
            "no execution binding present; process-instance attribution unavailable");
    };
    // version, agent match, pid != 0, pid_start_time_ticks != 0,
    // boot_id != [0;16], exe_content_sha256 != [0;32]
}

Assessment: correct and correctly scoped. Three things are right about it:

  • Absence is reported as passing, not failed. A packet without a binding is not attributable to a process instance; that is a statement about what the record can support, not a defect in the record.
  • The success message says "NOT independently observed" in the record itself, so a consumer reading the report cannot mistake a self-report for an observation.
  • The call site comment at :266-268 states it "Does NOT affect the trust floor: a self-report cannot raise evidence strength". The trust-floor derivation at :270-280 does not reference the R15 result. Verified by reading the derivation.

4.3 check_temporal_validity — unchanged, and the P0

prod/…/verification.rs:535-585. Byte-identical to main (both bodies extracted and hashed: dbafa0086c1b34af). It performs three comparisons:

if decided < issued_at                     → "decision predates issuance"
if decided > exp                           → "decision after expiry"
if action.performed_at > exp               → "action after expiry"
if action.performed_at < decision.decided_at → "action before its decision"

Every comparison is between two values carried inside the packet. VerificationContext (:29-43) carries issuer keys, counterparty keys, revoked JTIs, trace data and receipt data — and no clock.

Finding L-7 (P0, all branches with this file). A packet whose internal timestamps are mutually consistent passes regardless of how far they sit from real time. Combined with the absence of any replay rule among R1–R15, a captured packet remains verifiable indefinitely and a fabricated one can be dated arbitrarily. The system's temporal claims are internal-consistency claims only.

The fix is small — a now_ms field and a bound — and the fact that R15 was added without adding it is the notable part.

5. aip-reconcile — the verdict engine

5.1 Verification order

reconcile.rs:5-9 declares it, and the code follows it:

structure → expected signature → expected window → observer signatures → observer trust → chain/continuity → identity → decision id → binding → action → parameters → time → strength → result. A failed prerequisite is never skipped and never upgraded.

prologue (:1131-1213) implements everything the two entry points share and returns a finished record on early exit, so a failed prerequisite cannot fall through — there is no path that continues past it.

5.3 precondition_holds — read in full, findings

reconcile.rs:89-137. See Report 04 §2.1 for the table.

Finding L-8 (P3). SensorIntegrityFailure and ContinuityFailure are the only two classes with no structural precondition — their arm is strength >= EvidenceStrength::Attested alone. Every workload-directed verdict must present a witness in the record; neither observer-directed verdict must. For a system whose threat model includes a host that benefits from discrediting its observer, the asymmetry runs the wrong way.

Mitigating: classify_observer_error (:209-228) is careful about which failures earn Proven — signature arithmetic does, a bad local trust anchor does not — and the match is exhaustive so a new variant breaks the build. The care is present at the classification site; it is the precondition that is thin.

Finding L-9 (P2). Reconciliation (result.rs:679-699) has fourteen pub fields. ActionComparison's positive variants are protected by a private-field seal with pub(crate) constructors; the record carrying the verdict is not. Any consumer crate can construct a verdict directly, bypassing finish() and precondition_holds. The crate's own consumers do exactly this (aip-containment/tests/containment.rs:104).

The authors identified constructor control as the correct mechanism and applied it one level too shallow.

5.4 compare_action and place_transition — structural read only

reconcile.rs:385-689. Read at the level of doc comments and control-flow shape, not statement by statement. Two properties are stated and appear consistent with the code read:

  • A transition placed before the decision "is not the authorized action, whoever claims it — and it also disqualifies presence evidence of the same connection", i.e. the "existed, but was not made" case.
  • "Host claims only ever restrict a verdict."

NOT DETERMINABLE FROM CURRENT CODEBASE at this audit depth: whether every path through compare_action honours the second property. It requires a statement-level read of 230 lines and is the highest-value remaining target for a follow-up pass.

6. aegis-quantum (valladder / aipv4 only)

6.1 circuit-breaker/src/lib.rs:27-135 — read in full

pub struct CircuitBreaker {
    window_ns: u64,
    threshold: usize,
    connections: HashMap<ConnectionKey, ConnectionState>,   // unbounded
}

record_event (:65) does self.connections.entry(*key).or_insert_with(…). No method removes an entry. reset (:109) clears one connection's timestamps and leaves the entry. reset_all (:117) clears the map and is called by nothing on a timer or a bound.

Finding L-10 (P1). Per-key memory is bounded (the deque cannot exceed threshold + 1 before tripped short-circuits further pushes), but the number of keys is not. An adversary varying the connection tuple allocates one entry per tuple without limit, in the component whose documented purpose is to stop "one rogue agent hammering an endpoint in a tight loop."

Finding L-11 (P3). new() (:52) computes window_ms * 1_000_000 with unchecked u64 multiplication and validates neither argument. threshold = 0 trips on the first event; window_ms = 0 yields a one-nanosecond window.

Finding L-12 (P3). Once tripped, the timestamp deque is retained indefinitely — record_event returns at :76 before any eviction runs. Tripping the breaker is the cheapest route to permanent per-key retention.

Finding L-13 (P3). timestamp_ns is caller-supplied and assumed monotonic. Nothing enforces it. The eviction cutoff is timestamp_ns.saturating_sub(self.window_ns), so a caller feeding non-monotonic values shrinks the cutoff and stops eviction early.

Finding L-14 (P1) — the test that does not test this. stress-tests/tests/lru_exhaustion_test.rs (read in full, 47 lines) calls simulate_lru_saturation and MockLruSessionMap, both defined at stress-tests/src/lib.rs:19,84. Neither test constructs a CircuitBreaker. The crate depends on aegis-quantum-circuit-breaker but the exhaustion tests do not use it. Two passing tests named for a bound the product code does not have.

6.2 userspace/src/pqc.rs — read 1–200

Finding L-15 (P1). process_packet_event (:157-165) logs the event's addresses and discards it, then calls hybrid_x25519_kyber768_key_exchange(). That function (:90-131) creates client_secret, server_secret, and the Kyber keypair in the same process, encapsulates to a public key it just made, decapsulates with the private half it still holds, and compares two secrets derived entirely from key material it owns. secrets_match is arithmetically always true.

There is no peer, no socket, no session-map write. The doc comment is honest (:152 "For TRL-4, we simulate the full round-trip"); the crate description and the type name PqcValidationReport are not.

Finding L-16 (P3). algorithm is reported as "Kyber-768 (ML-KEM)". The dependency is pqcrypto-kyber 0.8.1, which implements round-3 Kyber. FIPS 203 ML-KEM is a different construction. The label conflates them.

Finding L-17 (P2). pqcrypto-kyber = "0.8" and pqcrypto-traits = "0.3" are caret ranges on cryptographic dependencies.

Not a finding — hybrid_session_hash (:134-142) is correct: domain-separated under AIRON-AEGIS-HYBRID-v1, both secrets length-prefixed before hashing. The construction is the recommended hybrid pattern. It is exercised only against itself.

2. Canonical encoding

The single most consequential cryptographic change across the six branches.

2.1 The defect on main (and four other branches)

main/aip-standalone/aip-core/src/capability.rs:208-231 builds the signing payload by raw concatenation:

buf.extend_from_slice(jti);
buf.extend_from_slice(issuer_id.as_bytes());
buf.extend_from_slice(agent_id.as_bytes());
…

…

Three distinct failures:

  1. Not injective. issuer_id = "ab", agent_id = "c" and issuer_id = "a", agent_id = "bc" produce identical bytes. A signature over one is a valid signature over the other.
  2. Not domain-separated. Nothing distinguishes a ScopedToken preimage from a DelegationToken preimage. A signature made in one context can be presented in another.
  3. expires_at is not covered at all. The field the verifier subsequently enforces is absent from the bytes the issuer signed.

The custom-action encoder compounds (1): ScopeAction::Custom(s) is encoded as 0x01 ‖ s ‖ 0x00, so a custom action containing an interior NUL is ambiguous with two adjacent actions, and the 0xFF allowed/denied separator is a byte a custom action can also contain.

2.2 The fix on prod

put_domain(&mut buf, SCOPED_TOKEN_DOMAIN);   // "AIP/ScopedToken/v1"
buf.extend_from_slice(jti);                  // fixed 16 bytes
put_str(&mut buf, issuer_id);                // u32-LE length prefix
put_str(&mut buf, agent_id);
encode_scope(&mut buf, scope);
put_u64(&mut buf, issued_at);
put_opt_u64(&mut buf, &expires_at);          // explicit presence byte

All three failures are closed. put_opt_u64 gives None and Some(0) distinct preimages, which is the difference between "unbounded authority" and "already expired" — the two most consequential values the field can take.

2.1 What B-1 and B-2 meant together — and what closing them changed

Superseded 2026-09-06. Both were closed by prod and independently verified. The analysis below is retained because it explains why they were the two that mattered, and because §2.1a records what the closure did and did not buy.

Individually each was serious. Together they composed: B-2 let an attacker holding any trusted issuer key insert themselves into a delegation chain, and B-1 removed the time bound that would otherwise limit how long a captured or forged chain remained usable. The system's central claim — that an evidence packet establishes who authorized an action and when — was held by neither half on any branch.

2.1a What the closure bought, and what it did not

B-2 is fully closed. The check is unconditional — inside verify_delegation_chain, which every caller reaches — so nothing can be left behind. aip-service inherits it without changing a line.

B-1 is closed in the protocol and not adopted by the service. The obligation that design creates is on the consumer, and aip-service does not meet it. That is B-1a.

The two fixes therefore illustrate the same lesson from opposite sides: an unconditional check propagates for free, an opt-in one propagates only as far as someone remembers to opt in. B-10 — aip-service being a member of no workspace — is why nobody did.

prod narrowed B-2's surface materially: because expires_at is now covered by the hop signature, a forged expiry fails as SignatureInvalid rather than being accepted. The identity substitution itself is untouched.

REPORT 07

IP / Patent Engineering

Written for a technically competent, skeptical reader. Nothing here is a legal opinion. The question addressed is narrower and answerable from source: which structures in this repository are concrete, non-obvious implementations rather than restatements of known practice, and are they described in the code with enough specificity to support a claim?

Novelty is assessed against what the code does, not what the documents say. Where a mechanism is a competent application of known art, that is stated plainly — an audit that calls everything novel is worthless.

1. Candidate structures, ranked

1.1 The single-choke-point verdict precondition — strongest candidate

Location: prod/aip-standalone/aip-reconcile/src/reconcile.rs:89-183.

What it is. Every result class the engine can emit passes through one predicate, precondition_holds(result, strength), which asks whether the evidence visible in the record being emitted permits the class being proposed. Per-branch logic decides which class to propose; this decides whether it is allowed. A proposal that fails is not an error — it is rewritten to (CannotProve, Heuristic, InvariantNotSatisfied).

Why it is structurally interesting. The separation of proposal from permission, with a fail-closed rewrite rather than a rejection, means that a future edit which forgets to establish a precondition degrades the verdict instead of asserting one. The code says this explicitly of coverage_recomputed:

PhantomClaim cannot leave finish without it, so a future edit that forgets the recomputation downgrades to CannotProve instead of asserting non-execution.

That is a maintenance property expressed in the type and control flow rather than in a comment or a review checklist.

Prior art it must be distinguished from. Policy decision points with obligation checks (XACML and descendants) separate decision from enforcement. Static analysers use lattice joins to keep uncertainty absorbing. What is not standard here is the combination of (a) an epistemic strength ladder in which the top class is reserved for facts a third party can recompute from held bytes, (b) per-class structural witnesses rather than scores, and (c) equality rather than threshold comparison on strength, so over-claiming is downgraded as readily as under-claiming.

Specification quality: high. The preconditions are exhaustively matched, the rationale for each is in the doc comments, and the fail-closed direction is stated.

1.2 The two-axis warrant ceiling with no arithmetic — strong candidate

Location: prod/aip-standalone/aip-warrant/src/warrant.rs:172-280.

What it is. The permitted response is min3(result_cap, strength_cap, severity_cap), where each cap is an explicit match, followed by monotone lowering only:

if unavailable || !cited || protected  → response = min(response, Alert)
if response == Contain && !policy.autonomous_containment → Alert

Why it is structurally interesting. The module doc states the design constraint directly: "Nothing here computes a product of the two axes." The usual approach — multiply severity by confidence, threshold the product — is precisely what this refuses. A high-severity, low-evidence finding cannot borrow authority from its severity. Each axis independently caps; none can raise.

Prior art it must be distinguished from. CVSS-style scoring, risk matrices, and alert-scoring in SIEM products all compose severity and confidence into a scalar. The distinguishing feature is the refusal to compose, plus the enumerated set of monotone lowering conditions (unavailability, absence of citation, protected identity, operator policy), each of which names an epistemic or governance condition rather than a numeric weight.

Specification quality: high, and the ordering of ResponseClass is declared with the invariant that every cap is a min against it.

1.3 Host-authored coverage re-derivation — strong candidate

Location: prod/aip-standalone/aip-reconcile/src/reconcile.rs:1043-1120 (recompute_coverage).

What it is. The collector signs a batch that includes coverage fields — claimed_from_ms, claimed_to_ms, active_mechanisms, probe_run_id — every one of which is authored by the host-side probe. The reconciler does not read them. It re-derives, from the attested batches alone, whether the window was continuously sampled by one probe run using a kernel-pushed mechanism, anchoring the end of the window to health_emitted_at_ms, a time the collector itself signed.

The reasoning in the doc comment is the substance of the invention:

a compromised host [could] manufacture coverage over an interval nothing sampled — and a PHANTOM_CLAIM is precisely a statement about such an interval.

Why it is structurally interesting. A signature over host-authored claims authenticates the collector's relay, not the claim's truth. The distinction is routinely missed. The mechanism — signed relay of an untrusted claim, plus independent re-derivation by the consumer, plus a verdict class that exists only to state a negative about an interval — is a specific and describable arrangement.

Prior art it must be distinguished from. Remote attestation quotes, transparency-log consistency proofs, and audit-log gap detection all touch this. The specific arrangement of probe (untrusted, keyless) → collector (trusted, signing, off-host, assigns sequence and clock) → reconciler (re-derives coverage rather than reading it) is what would need to be claimed.

1.4 Keyless probe / off-host attestation boundary — moderate candidate

Location: prod/aip-standalone/aip-observe/src/attest.rs:1-95.

What it is. The observed host holds no signing key by construction: probe has no key field and no signing method; ObservationBatch has no signature field; sequence is assigned by the collector; attested_at_ms is the collector's clock. The signed head is computed from a domain-separated preimage and never carried, so no supplied hash is trusted. key_version is inside the preimage, so rotation is anchored rather than retrofitted.

Assessment. The individual elements are known practice (remote logging with signing at the collector; computed-not-carried digests; key versioning in the preimage). What is well done rather than novel is the completeness — the module doc enumerates exactly what an attacker with root on the observed host can and cannot forge, and the type definitions match the claim. This is strong engineering and weaker patent material than 1.1–1.3.

1.5 Temporal attenuation enforced against a valid signature — moderate candidate

Location: prod/aip-standalone/aip-core/src/delegation.rs:220-231.

What it is. After authenticity is established, the chain separately rejects a hop whose expires_at outlives its parent's — including the None case, where an unbounded child of a bounded parent is refused. The ordering is deliberate and documented: a forged expiry reports SignatureInvalid, a genuinely over-delegated one reports AttenuationViolation. The two are different accusations and the code keeps them distinct.

Assessment. Capability attenuation and monotone expiry narrowing are established art (macaroons, biscuits, SPKI/SDSI). The refinement worth noting is the error-class separation — distinguishing "this was tampered with" from "your issuer exceeded their authority" is diagnostically and forensically meaningful and is rarely implemented.

2. Structures that are competent but not novel

Stated plainly so the portfolio is not padded:

  • Prefix-free canonical encoding with domain tags. Correct and necessary (Report 05 §2), but this is textbook — length-prefix everything, lead with a domain separator. Its value here is remedial, not inventive.
  • RFC 6962 Merkle with 0x00/0x01 leaf-node separation. Explicitly implementing a published standard.
  • Ed25519 / SHA-256 usage. Library calls.
  • The 17-gate containment chain. Thorough and well-ordered, but a gate sequence is a checklist; the novelty in this area sits in 1.1 and 1.2, which decide what reaches the gates.
  • X25519+Kyber hybrid combiner. The construction is correct (domain-separated, length-prefixed) and is the recommended pattern; it is not new, and here it is not exercised across a trust boundary at all (Report 03, I-20).

3. Material risks to any filing

These are engineering facts with IP consequences, stated because a patent examiner or an acquirer's technical diligence will find them.

IP-1 (high). The containment path — a plausible subject of any "autonomous accountability enforcement" claim — is unreachable from the engine (Report 04 §3, EXECUTION-PROVEN). A claim describing an end-to-end system that observes, reconciles, warrants and contains would not be supported by a reduction to practice, because the fourth stage cannot be entered from the third. The demonstrated system stops at Constrain.

IP-2 (high). The three strongest candidates (1.1, 1.2, 1.3) exist only on claude/codebase-production-readiness-wm6idp, a branch that is not merged to main. Whatever is filed must be anchored to that branch's tree; main does not contain the described mechanisms.

IP-3 (medium). All 103 commits carrying this work have a single machine author identity (Report 02 §2). Inventorship for machine-generated contributions is unsettled and jurisdiction-dependent. This needs a documented human conception and reduction-to-practice record independent of the commit log. That record does not exist in the repository.

IP-4 (medium). SYNTRIASS, NEXORA, GHOST and AIRON appear as domain-tag namespaces across the code (SYNTRIASS/GHOST/…, SYNTRIASS/NEXORA/…, AIRON-AEGIS-HYBRID-v1). These are wire-format constants; changing them later is a breaking protocol change. Name clearance should precede, not follow, any public deployment.

IP-5 (low). aegis-quantum carries license = "UNLICENSED" in its workspace package metadata while depending on third-party crates. This is a licensing hygiene item, not an infringement finding.

4. Drafting guidance implied by the code

If claims are drafted, the following are the load-bearing specifics that distinguish this implementation from the general idea, and they should appear in the specification because they are what makes it non-obvious:

  1. Strength comparison is equality, not a threshold, for content-derived verdicts — over-claiming is downgraded, not accepted.
  2. The top evidence class is defined by recomputability by a third party from held bytes, not by source or by confidence.
  3. Positive action evidence is unconstructible outside the engine (a private field with pub(crate) constructors), so a caller cannot supply a match.
  4. Coverage is re-derived from batches, with the window's end anchored to a time the collector signed.
  5. The response ceiling is a min of independent caps, with an explicit prohibition on composing the axes arithmetically.
  6. Observer-directed and workload-directed findings have different targets (ResponseTarget::Observer vs Workload), so a sensor fault can never authorize action against the workload.

Item 6 is worth emphasising: it is a small piece of code and it forecloses a whole class of attack in which compromising the sensor becomes a route to acting on the workload.

3. What is genuinely defensible

Also stated without cushioning, because a report that only lists problems is as useless as one that only lists strengths.

The epistemic discipline is real and it is unusual. Three properties, all CODE-PROVEN and TEST-PROVEN on prod:

  • The default verdict is "cannot prove". Absence of evidence yields no verdict, enforced through one choke point, with a fail-closed rewrite.
  • The highest evidence class is defined as recomputable by a third party from held bytes, and content read from the observed host is structurally barred from it because that content is root-forgeable.
  • Coverage claims authored by the observed host are re-derived from the attested batches rather than read, because a signature over a host's claim authenticates the relay, not the claim.

Most systems in this space compose a severity and a confidence into a score and threshold it. This one explicitly refuses to: "Nothing here computes a product of the two axes." Each axis independently caps the response; none can raise it. That is a defensible architectural position and it is implemented as stated.

The observer boundary is designed rather than asserted. The probe on the observed host holds no key, has no signing method, and its batch type has no signature field. The collector, off-host, assigns the sequence number and the timestamp. The module documentation states precisely what an attacker with root on the observed host can forge (the content of observations offered) and cannot (an attestation of them), and names the remaining transport assumption as a deployment obligation rather than glossing it.

The test posture on prod is serious. 787 tests including 3,320 lines of dedicated adversarial tests. The delegation test that constructs a hop validly signed by the genuine key which nonetheless outlives its parent, and requires rejection, is the kind of test that only gets written when someone has thought about the actual threat rather than the feature list.

4. Where the tests do not cover what they appear to

Three cases, because diligence will find them and it is better that they appear here first (Report 06 §4 has the detail):

  1. Containment tests verify seventeen gates against hand-built records that the engine cannot produce.
  2. The circuit-breaker exhaustion test verifies a mock LRU defined in the test crate; the real CircuitBreaker has an unbounded HashMap with no eviction path — a remote memory-exhaustion vector in the component whose stated purpose is defending against runaway agents.
  3. The PQC tests verify a loopback round-trip; none supplies a wrong ciphertext, a tampered key, or a counterparty.

None of these tests is defective. The gap is between what they assert and what their names imply.

5. Governance

All 103 commits on prod — 66,074 lines — carry a single machine author identity, over fourteen days. Commit metadata records no independent human review of any commit.

For an engineering-velocity narrative this is a strength. For diligence it raises two specific questions that the repository cannot currently answer: who reviewed the cryptographic changes, and what record establishes human conception for any intellectual property claim (Report 07, IP-3). Neither is a code defect. Both are answerable with process, and the answer should exist before it is asked.

6. Position

The asset is the reconciliation engine and the observation boundary, on one unmerged branch. They encode a defensible and unusually disciplined position on what a system may claim to know and on what evidence.

The liabilities are specific, enumerable, and mostly small. Two P0 defects that are each a few lines. A containment path that needs a decision before it needs code. A service tier that was never in scope for the work that was done. A post-quantum component that measures latency rather than establishing a secret with anyone.

What would change the position most, in order:

  1. Merge prod to main, or state clearly that main is not the product. The current arrangement means the repository's default branch understates the work by 42,000 lines and 644 tests.
  2. Close the two P0s. They are small and they sit under the central claim.
  3. Answer whether autonomous containment is meant to be reachable, then write the end-to-end test either way. The test documents the answer.
  4. Either bring the service tier into scope or scope it out explicitly. Byte-identical handlers across four branches is a decision by default.
  5. Stop describing the system as quantum-resistant until a PQC exchange has a counterparty.

None of the five is research. All five are engineering with known shapes.

2. B-1 — verifier-supplied verification-time bound

Status: CLOSED in aip-protocol. NOT ADOPTED in aip-service.

2.1 What was built, and it is well built

CODE-PROVEN. aip-protocol/src/verification.rs adds rule R16 VERIFICATION_TIME_BOUND plus two context fields:

pub verification_time_ms: Option<u64>,
pub future_tolerance_ms: u64,

Three design decisions are correct and worth naming:

  1. The time is supplied, never read from the system clock. An offline verifier, an air-gapped verifier and a test all need to state what "now" means to them. Reading SystemTime::now() inside the verifier would have made the rule untestable and wrong for delayed verification.
  2. Absent a time, R16 is recorded as NOT EVALUATED, not as a pass. The report carries evaluated: bool per rule, verification_time_checked, and not_evaluated().
  3. The bound is not "the authority must still be valid now". A historical packet stays verifiable after its tokens expire — offline verification depends on that — and whether the authority was valid at decision time remains R10's question. Conflating the two would have broken archival verification, and the test p0_1_a_historical_packet_stays_verifiable_after_its_authority_expires pins it.

aip-verify surfaces the gap to a human: main.rs:224 prints note: <rule> was NOT evaluated — <detail> for every unevaluated rule.

(An earlier pass of this addendum provisionally recorded the CLI as silent. That was wrong — the grep used the wrong symbol. Corrected here rather than removed, because a withdrawn finding is itself a finding about the audit.)

2.2 The residual, stated precisely

valid is computed as:

let valid = e.checks.iter().all(|c| !c.evaluated || c.pass);

An unevaluated rule therefore does not make a report invalid. Prod's own test asserts this openly:

p0_1_without_a_bound_the_rule_is_not_evaluated_rather_than_passed assert!(report.valid); "Still valid — an unevaluated rule is not a failure — but a consumer can tell the difference, which is the whole point."

This is the right decision, not a defect. Making valid false for an unevaluated rule would conflate "could not check" with "failed", which is precisely the CANNOT_PROVE / FAILED distinction the whole codebase is built on. The obligation it creates is on the consumer: reading .valid alone is misuse of the API, in the same way that reading Corroboration::is_corroborated() == false as "nothing wrong" would be.

REFERENCE 12

AIRI Specification

Status: implemented, not promoted. See AIRI_LIMITATIONS.md for what is established and what is not, and AIRI_MIGRATION.md for versioning.

1. What AIRI is

A framework-neutral schema for what an AI agent's own runtime says it did: which model it asked for, which tool it invoked, with which parameters, under which authorization, in which process.

One schema covers LangChain, LangGraph, LlamaIndex, AutoGen, CrewAI, OpenAI-style tool calling and bespoke runtimes. Adapters are thin translators into these types. No framework is a trust anchor, and nothing in the implementation branches on a framework's name to grant anything.

2. What AIRI is not

An AIRI event is not evidence that anything happened. It is evidence that the agent said so.

The signing key belongs to the agent. The clock belongs to the agent. The process that emits the event is the process under scrutiny. Every guarantee is of the form "this statement was made by this agent about this execution and has not been altered since" — never "this occurred".

This is enforced structurally, not by convention:

GuaranteeMechanism
An event cannot claim independenceNo constructor, field or enum variant exists by which it could
"Independent evidence agreed" is unforgeableCorroborationSeal is #[non_exhaustive]; only corroborate() can produce one
AIRI cannot move a verdictcorroborate and integrate contain no expression producing a ReconciliationResult or an EvidenceStrength

3. Position in the chain

AIP Identity → Authority/Delegation → Authorization → ExpectedExecution
                                                            │
                        ┌───────────────────────────────────┴──────────────┐
                        │                                                  │
                ── AIRI (agent-signed) ──                  ── aip-observe (collector-signed) ──
                self-authored claims about                 off-host, keyless probe,
                model / tool / framework / subprocess       kernel-pushed events
                        │                                                  │
                        └───────────────────┬──────────────────────────────┘
                                            ▼
                              aip-reconcile (semantics unchanged)
                                            ▼
                          Warrant → Containment → NEXORA Proof

The two inputs are asymmetric on purpose. Reconciliation is where the asymmetry is spent.

4. Event model

ModelInvocationObserved is named "observed" by the specification and is not independent observation. The observer is the framework, inside the process under scrutiny. It carries no more weight than any other self-report, and corroborate will not accept it as corroboration of itself.

"Externally observable" means a host observer could in principle see a matching kernel event. A hosted-model inference leaves a socket, but that socket is the tool layer's evidence; attributing it to the model layer would count one fact twice.

Three lineages kept apart

  • identity lineage — aip-agent, which agent document descends from which
  • authority lineage — delegation chains, who granted what to whom
  • application lineage — parent_execution_id, which run spawned which

Nothing in AIRI reads parent_execution_id to widen scope. Being spawned by a run confers no authority; a child carries the same expectation or none.

6. Canonical encoding

preimage = put_domain("SYNTRIASS/AIRI/EVENT/v1")
         ‖ put_u16(version)
         ‖ put_str(agent_id)
         ‖ execution_id                      (fixed 16, length-prefixed)
         ‖ put_opt_bytes16(parent_execution_id)
         ‖ put_opt_bytes16(decision_id)
         ‖ put_u64(sequence)
         ‖ prev_event_hash                   (fixed 32, length-prefixed)
         ‖ put_u64(emitted_at_ms)
         ‖ framework.encode()
         ‖ put_opt(runtime_binding.identity_bytes())
         ‖ put_u8(kind_code) ‖ payload.encode()

Every variable-length field is length-prefixed (u32 LE) and every optional field carries a presence byte, so the encoding is injective. The domain tag leads, so an AIRI signature cannot verify as a ScopedToken, a DelegationToken, an observer head, a reconciliation record or a warrant, and none of theirs can verify here.

Neither collides with any of the fifteen domains already in the repository.

7. Commitments, not payloads

Prompts, tool arguments, model outputs and argument vectors never enter an event. Only commitments do:

commit(x) = SHA-256( put_domain("SYNTRIASS/AIRI/PARAM_COMMITMENT/v1") ‖ put_bytes(x) )

Domain-separated rather than a bare SHA-256, so a digest computed elsewhere in the system — a packet hash, an observer head, a Merkle leaf — cannot be presented as a parameter commitment.

The Python SDK commits JSON with sort_keys and fixed separators, so the same logical arguments commit identically regardless of dict ordering. Without that, a verifier comparing two commitments of identical arguments would see a substitution that never happened.

8. Chains

Events for one execution form a hash chain. prev_event_hash is the SHA-256 of the previous event's signed preimage.

Detected: replay, duplication, drop, reordering, splicing from another execution or agent, and deletion hidden by renumbering.

Not detected: truncation at the head. A prefix of a valid chain is a valid chain, and nothing inside the chain distinguishes "the run ended here" from "the rest was withheld". Closing this needs either an observer or a verifier that insists on a signed completion. The limit is tested (chain.rs::dropping_the_last_event_is_not_detectable_and_that_is_documented) rather than papered over.

9. Corroboration

corroborate() compares one claim against collector-signed observation.

OutcomeMeaning
NotEvaluated(reason)Not compared. Carries why, so silence is never read as "clean".
Corroborated(seal)Independent evidence covering the window and the instance is consistent with the claim.
Uncorroborated{reason}The observer covered the claim and did not see it. The epistemically valuable case.
Contradicted{detail}Observation contradicts the agent's own account.

Order of evaluation, each step failing toward "cannot say":

  1. Is this kind externally observable? → NotExternallyObservable
  2. Is there a runtime binding to join on? → NoRuntimeBinding
  3. Did the observer declare coverage? → ObserverUnavailable
  4. Do any batches overlap the window? → WindowNotCovered
  5. Is the action class mappable? → ActionClassNotComparable
  6. Does any observation refer to the claimed instance? → InstanceNotObserved
  7. Does any observation match the class? → Corroborated / ActionClassAbsent

Step 5 matters more than it looks: an unmappable action class returns NotEvaluated, never Uncorroborated. Turning a vocabulary gap into a phantom claim would be the worst false positive this system can make.

10. The three tool layers

1. Requested invocation    ToolInvocationRequested
2. Runtime execution       ToolExecutionReported
3. External effect         — no event asserts this —

An HTTP 200 is evidence of layer 2. A proxy, a stub, a replayed cassette, a compromised client, a load balancer that acknowledged and dropped, or a database that returned success and rolled back all produce a 200. There is no method in the SDK and no variant in the Rust types that asserts layer 3, because the process that made the call cannot know.

Only independent observation can speak to layer 3, and even then the ceiling is Attested — content read from the observed host is root-forgeable.

11. NEXORA

Two carriage points, both live.

As a Merkle leaf. An AIRI event commits under LeafKind::AiriEvent (code 0x09), appended to the frozen set rather than renumbering it.

As a proof component. NexoraProof (package version 2) carries an optional AiriBundle under Component::Airi (0x0A): the agent id, the key the package says signed the events, and the events themselves in emission order.

In both cases what is committed is the event's signing preimage — the exact bytes the agent signed — so a verifier checks one artefact rather than trusting a re-serialisation round-trip.

What the offline verifier does with it

verify_nexora_proof re-derives:

  1. every event's signature, against the key the verifier anchored;
  2. the chain, re-walked from the package's own bytes;
  3. that every event's agent_id is the bundle's.

The result is a ComponentVerdict — Verified, Absent, or Unverifiable(reason) — plus airi_events_verified. It is never an upgrade to any other component.

The package cannot choose the key it is judged against. If the verifier anchored a key for this agent, that key is used and the package's must match it; a package naming a different key is refused with "does not anchor", not quietly verified against the one it supplied. Without that rule an assembler could sign a fabricated chain with its own key, put that key in the bundle, and have every signature check out.

A Verified verdict reached under a self-supplied key (verifier anchored none) means "internally consistent", which is weaker than "signed by the agent the verifier trusts" and must not be read as the latter.

Symmetry

AIRI cannot raise a verdict and a broken AIRI bundle cannot lower one. The reconciliation rests on the observer's evidence; a defect in the agent's own account is recorded as its own component verdict rather than leaking into the result. Both directions are tested (aip-nexora/tests/airi.rs).

12. Reconciliation

AIRI produces an AiriAnnotation that sits beside a Reconciliation, never inside it. annotate() takes the reconciliation by shared reference and returns a new value; it contains no expression producing a ReconciliationResult or an EvidenceStrength.

tests/reconcile_integration.rs drives the real engine and asserts the verdict and strength are identical with and without AIRI evidence present, in every corroboration shape.

A reconcile_airi_claim entry point that could reach PHANTOM_CLAIM from an uncorroborated AIRI claim is deliberately not implemented. See AIRI_MIGRATION.md §4.

The actor should not control the evidence used to judge the actor.

Everything below follows from it.

The agent and the collector are the two signing parties that matter, and the architecture's entire value is that the agent cannot reach the collector's key.

3. Adversary

Capability: full control of the agent process — arbitrary code, the agent's private key, the process clock, all framework instrumentation, all Python-level telemetry, and root on the observed host.

Goal: have Vanian certify an action that did not happen, or fail to record one that did.

Out of scope: compromise of the collector, of the decision point, or of the verifier's anchors. Those are different trust boundaries with their own controls; AIRI assumes them intact and is worthless if they are not.

5. Deployment obligations

Not code properties. A deployment that skips these gets less than the tests suggest.

  1. Transport authenticity from probe to collector. aip-observe states this: the registry lives at the collector, but proving a batch really came from the registered probe is the transport's job.
  2. Observer key custody. Off-host, in an enclave or HSM. An observer key on the observed host reduces the whole system to self-report.
  3. Agent key custody. Mode 0600 or tighter, ideally an HSM. The SDK refuses group- and world-readable files but cannot defend a key already read.
  4. Anchor distribution. Verifiers must obtain agent, observer and decision-point public keys through a channel the agent cannot influence.
  5. Rate limiting and back-pressure at the collector.
  6. Commitment policy. Which fields are committed, and the retention of the plaintext they commit to, is a deployment decision with privacy consequences.

7. What AIRI actually buys

Given all of the above, the honest summary:

AIRI does not make an agent's claims trustworthy. It makes them specific, bound, and checkable — so that when independent observation exists, the two can be compared, and when it does not, the system says so rather than guessing. The valuable output is not Corroborated; it is Uncorroborated and NotEvaluated, which are the two answers a self-reporting system normally cannot produce at all.

2. Rules

  1. A verifier refuses an unknown version rather than interpreting it. Fields may have moved; a best-effort parse of an unknown layout is how a signature ends up covering something other than what a verifier reads.
  2. The domain tag carries the version. A v2 event signs under SYNTRIASS/AIRI/EVENT/v2, so a v1 verifier cannot be tricked into accepting a v2 event and vice versa. The version is belt as well as braces.
  3. Leaf codes are frozen. A leaf committed today keeps verifying.

  4. A false-positive budget agreed with whoever operates it, because the first production week decides whether the system stays switched on.

5a. The v1 → v2 package break

NEXORA_PROOF_VERSION moved from 1 to 2 to carry AiriBundle. A v1 package is refused by a v2 verifier (InvalidReason::UnsupportedVersion), not reinterpreted.

The AIRI component is appended after Commitment, so every field a v1 package encoded sits at the byte offset it always did.   • A v1 event verifies against a v1 verifier indefinitely.

  • A NEXORA package containing an AIRI component requires a v2 verifier. A v1 verifier refuses it by version, which is the loud failure, not a misparse.
  • The Python SDK and the Rust crate must ship together. The parity vectors are the contract; a mismatched pair is a build failure by construction.

3. The distinction that matters

The load-bearing statement

The system does not treat a valid signature over a false statement as proof of the underlying execution.

This is observed behaviour, not a slogan. In Scenario 1 the AIRI event verified — authorship and integrity were intact and verify_airi_event correctly returned Ok. The claim still resolved to SELF_REPORTED with a cardinality divergence flagged (1 claimed, 0 observed), because two mechanism-independent observers covered the window and saw nothing. A perfect signature over a false statement bought the actor nothing.

The converse case is equally load-bearing. Scenario 6 claimed an act that leaves no host-visible mark. The correct answer is “cannot be established”; the tempting wrong answer is “unsupported, therefore false”. It stayed SELF_REPORTED and was never called false.

4. The boundary that moved

New at 12767ea

Observation integrity is now treated as part of the evidence boundary.

Before 12767ea, a live, continuity-verified observer could be silently blind and still sign Active coverage — and a blinded window could drive a false PhantomClaim, which is an accusation that a claimed execution did not happen. After 12767ea, the coverage assertion is a function of the observer's own integrity state, and that state is inside the signed record. The fix is fail-safe and strictly monotone: every part can only turn a coverage claim into CannotProve, never the reverse, and it touches no verdict on the trusted-observation side.

Why the kernel behaves this way

Stated once, so the finding is checkable rather than anecdotal. The kernel gates a tracepoint's perf submission on the attached BPF program's return value in perf_trace_run_bpf_submit(), keyed per trace_event_call — per tracepoint, host-wide. Every perf_event_open consumer of that tracepoint therefore stops receiving samples. The ftrace submission path is separate and unaffected, which is exactly the asymmetry observed, and is what makes the diagnosis certain rather than plausible.

ADDENDUM F

Architectural Differentiation & USP

1. Why the architecture is different

Conventional AI-agent security and observability systems primarily address one or more of: policy enforcement, access control, prompt/input security, model security, agent observability, logging, traceability, governance. These are real problems and the products that address them are, in general, good at them.

Vanian's architectural target is a different question: autonomous intelligence accountability. The differentiating chain:

WHO
 → WHAT WAS AUTHORIZED
   → WHAT WAS EXPECTED
     → WHAT ACTUALLY EXECUTED
       → WHAT WAS INDEPENDENTLY OBSERVED
         → WAS OBSERVATION INTEGRITY ESTABLISHED
           → WHAT EFFECT CAN BE ESTABLISHED
             → WHAT CAN BE CRYPTOGRAPHICALLY PROVEN

Four structural commitments make that chain more than a diagram, each CODE-PROVEN and TEST-PROVEN:

  1. The actor does not control the evidence used to judge the actor. The probe on the observed host holds no key and has no signing method; the collector holds the key off-host, assigns the sequence and stamps its own clock.
  2. Coverage is re-derived, never read from the artifact being judged. A NEXORA package has no field in which to state its own coverage. Exactly one of five outcomes — AvailableAndEmpty — licenses a statement about something not having happened.
  3. Severity and evidence strength are never composed into a score. There is no confidence: f32 anywhere in the evidence path; the permitted response is a min of independent caps.
  4. The proof layer re-derives rather than trusts. The offline verifier ignores the carried result, re-runs the reconciler under the verifier's anchors, and refuses ClaimNotDerivable. CANNOT_PROVE cannot become PROVEN through packaging, export, import or transport.
Boundary of this claim

No claim is made that other companies cannot do these things. This section claims only that this is the problem Vanian is architected around, and that the mechanisms above are present in code with tests that exercise them.

The instructive case: co-resident eBPF tooling

The most useful competitive fact in this document is not commercial

Vanian's observation-integrity finding was produced by running a third-party eBPF observer alongside Sniffer Dog. The co-resident observer silently blinded it by attaching a program to the same tracepoint — a class of behaviour any eBPF security tool, Tetragon included, can exhibit entirely benignly.

Two consequences follow. First, benign and malicious interference are indistinguishable by effect, so the detector must key on the presence of a foreign program, not on intent, and the fallback must be INTEGRITY_UNKNOWN rather than “attack”. That is exactly what shipped. Second, any customer running Falco, Tetragon or Tracee alongside an observation-based accountability layer is in the reproduced scenario — which makes observation integrity a co-existence requirement, not only a security one.

The whitespace, stated conservatively

No vendor surveyed publicly positions the combination of (a) independent runtime observation with the observer's key off the observed host, (b) explicit observation-integrity semantics, (c) an execution-versus-effect distinction enforced by the absence of any event that could assert an effect, (d) CANNOT_PROVE as a first-class outcome, (e) offline re-derivation of a verdict by a third party, and (f) one accountability core across both software and physical autonomy.

This is a statement about public positioning as of September 2026. It is not a claim of technical exclusivity, and it should be re-tested before each fundraising cycle.

ADDENDUM R

Conclusion

The evidence supports a strong engineering position and does not support a finished product.

What is strong

The epistemic discipline is real, implemented, and unusual: a default verdict of “cannot prove”, an evidence ceiling that structurally bars host-derived content from the top class, coverage re-derived rather than read, a response ceiling that refuses to compose severity with confidence, and an offline verifier that re-derives instead of believing.

That discipline survived its first contact with an independent external observer, and — more tellingly — that same observer exposed a way to silently blind the observation layer, which was then reproduced deterministically and closed in production without weakening a single one of those properties.

What is not finished

The physical half of the thesis is architecture and documentation. There is no robot, no airframe, no external tracker, no hardware root of trust, no third-party security assessment and no field deployment. The UAS and robotics profiles are careful, honest and unvalidated against hardware.

What follows

The next value-creating milestone is not a feature. It is the first physical quantity established by an independent mechanism rather than asserted by the machine that moved — because that is the single step that turns “one accountability core, many autonomous worlds” from a design statement into an engineering result.

Engineering status

TRL 5 overall; AIRI/Sniffer Dog software accountability core approaching TRL 6; physical autonomous-system validation pending.
