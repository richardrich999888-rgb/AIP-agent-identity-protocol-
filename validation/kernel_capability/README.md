# Kernel capability probes — runtime evidence, not configuration strings

**Kernel of record** `6.18.44-fc-v185`
**Date** 2026-10-29
**Why** ADR-008 records the trap these probes exist to avoid

> `CONFIG_LSM="...,bpf"` in the boot string and `BPF_PROG_TYPE_LSM` present
> in BTF are **not** evidence that the feature works.

The same applies to `/sys/kernel/security/lsm`. An LSM name in that list
means the LSM is *registered*, not that a program can be loaded onto it or
that its decision reaches a caller. These probes replace inference with an
attempt.

## 0. Results

| Capability | Status | Strength |
|---|---|---|
| **Landlock filesystem enforcement** | **ENFORCEMENT_PROVEN** (ABI v7) | EXECUTION-PROVEN |
| **BPF-LSM program load** | **REFUSED — `EPERM`** | EXECUTION-PROVEN (negative) |
| BPF-LSM hooks compiled into the kernel | present in BTF | CONFIG-OBSERVED |

Raw records: `landlock-result.json`, `bpf-lsm-result.json`. Both are
regenerated by running the probes; neither is hand-written.

## 1. Landlock — proven, and it restricts root

Four predicates, all required, because any one alone is satisfiable by a
broken kernel:

| Predicate | Result | Why it is in the set |
|---|---|---|
| both files readable **before** restriction | ✅ | otherwise the fixture proves nothing |
| allowed subtree still readable after | ✅ | a kernel denying everything is not a sandbox |
| read outside subtree → `EACCES` | ✅ | the enforcement claim |
| write outside subtree → `EACCES` | ✅ | a second hook, no extra fixture |

The probe ran as **uid 0 with CAP_SYS_ADMIN effective** and was still
denied. That is the property that matters: Landlock binds the process, not
the privilege level.

**Scope limit, stated because the probe cannot exceed it.** This proves
filesystem read and write enforcement under ABI v7 on this kernel. It says
nothing about network rules, about any other hook, or about whether a
process *outside* the sandbox can detach it.

### A finding from the probe's own first failure

The first version wrote the child's result to a path outside the allowed
subtree. The kernel denied that write with `EACCES`, and the probe crashed.
That accident was a stronger demonstration than the designed one — a process
denied writing a file it had created moments earlier. The probe now reports
through an inherited pipe, because an open fd survives
`landlock_restrict_self` and a path under a handled-write ruleset does not.

## 2. BPF-LSM — compiled in, hooks present, and still refused

`BPF_PROG_LOAD` with `prog_type=BPF_PROG_TYPE_LSM` returns **`EPERM` with an
empty verifier log**. An empty log means the refusal happened *before*
verification, so it is a policy decision and not a program defect.

The differential rules out every innocent explanation:

| Probe | Result |
|---|---|
| `BPF_MAP_CREATE` | ✅ loads |
| `BPF_PROG_TYPE_SOCKET_FILTER` | ✅ loads, verifier runs (`processed 2 insns`) |
| `BPF_PROG_TYPE_KPROBE` | ✅ loads, verifier runs |
| `BPF_PROG_TYPE_SCHED_CLS` | ✅ loads, verifier runs |
| `BPF_PROG_TYPE_LSM` | ❌ `EPERM`, empty log |
| `BPF_PROG_TYPE_TRACING` (fentry) | ❌ `EPERM`, empty log |

Varied independently and with no effect: `attach_btf_id` ∈ {0,
`bpf_lsm_file_open`}, `expected_attach_type` ∈ {0, `BPF_LSM_MAC`}. All three
combinations return the same `EPERM`.

**Not a capability problem.** `CAP_BPF`, `CAP_SYS_ADMIN`, `CAP_MAC_ADMIN`
and `CAP_PERFMON` are all effective (only `CAP_SYS_RESOURCE` is dropped),
and `Seccomp: 0` — no filter is intercepting the syscall.

**The discriminator.** The two refused types are exactly the BTF-attached
program types that can read kernel memory. The only active policy in the LSM
list that separates that class is kernel lockdown:

```
/sys/kernel/security/lockdown -> none [integrity] confidentiality
```

Lockdown is in **integrity** mode. That is a well-supported attribution and
it is where the evidence stops: the probe did not toggle lockdown and so did
not isolate the specific kernel check. `selinuxfs` is not mounted, so
SELinux is not adjudicating here.

### Why this matters, and why it is not the old finding restated

The maturity addendum recorded, on kernel `6.18.44-fc-v24`, that
`CONFIG_BPF_LSM` was **not set** — BPF-LSM was absent from the build. That
made every BPF-LSM enforcement design architecturally unavailable.

This kernel is different in a way that changes the conclusion's *kind*:

- the option **is** set;
- the `bpf_lsm_*` hook stubs **are** in BTF;
- `bpf` **is** in the active LSM list;
- and loading is nonetheless refused by **host policy**, not by the build.

So the correct status for the active-interception tier is **deployment-gated,
not architecturally unavailable**. On a host with lockdown off and the same
kernel options, the probe would likely succeed — and `bpf_lsm_probe.py`
exists to settle that by attempt rather than by argument. Until it is run
there, the honest external phrasing remains "designed to support", never
"supports".

### What was deliberately not proven

Stage B would have proven *enforcement* by attaching a deny program to
`socket_connect` and requiring `EPERM` on a connect that worked moments
earlier, then requiring recovery after detach. It never ran, because the
load was refused first. It is retained in the probe, bounded three ways: the
attachment lives for one connect attempt, it is owned by a link fd the
kernel releases on close, and it runs in a forked child so even a crash
releases it. There is no path that leaves a host permanently unable to
connect.

## 3. Reproduce

```sh
python3 -B validation/kernel_capability/landlock_probe.py --fixture-dir "$(mktemp -d)"
python3 -B validation/kernel_capability/bpf_lsm_probe.py
python3 -B validation/kernel_capability/tests/test_btf.py      # 14 tests
```

Exit codes are the machine-readable verdict and never conflate the cases:
`0` proven, `1` present but did not enforce, `2` unavailable or blocked.

The BTF reader is 100 lines with no dependencies because `bpftool` is absent
and libbpf is not installed. It carries a regression test for the bug that
found it: `BTF_KIND_FLOAT` has no trailing payload — its width is in
`btf_type.size` — and a 4-byte entry for it drifts the cursor into a kind-0
header about 8,200 types later. A silently wrong walk is worse than a crash,
because a wrong `attach_btf_id` attaches a program to the wrong kernel
function.

## 4. Still absent on this kernel

`CONFIG_KPROBES`, `CONFIG_TCG_TPM`, `CONFIG_IMA`, `CONFIG_INTEGRITY`. The
kprobe and TPM blockers from the earlier record stand unchanged, so
`RootOfTrust::Tpm2` remains correctly unimplemented and the measured-boot
recommendations remain unexercisable.
